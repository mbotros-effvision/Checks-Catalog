Sitebulb, assessed for embedding into Snurra

Fits into Snurra: No API No public REST API or CLI — only push-only Cloud webhooks (aggregated) and a forthcoming read-only MCP; scheduled file-based source.

Sitebulb is an SEO website crawler & auditor — it crawls a site in a real Chromium engine and produces prioritised “Hints” across technical SEO, indexability, internal links, redirects, structured data, hreflang, accessibility (Deque axe‑core), security and Lighthouse performance. It ships as Desktop (installed) and Cloud (hosted) on one engine. The catch for embedding: it has no public REST API and no CLI — the only programmatic hooks are Cloud webhooks (aggregated audit‑level payload) and auto‑exported files. This page maps its capabilities, how it could realistically slot into Snurra’s worker, what it costs, and — held to a strict 100%‑certain bar — precisely which feasibility‑catalog checks it can cover.

Bottom line up front
Sitebulb crawls in real Chromium and produces 300+ prioritised Hints. Held to a strict bar it can cover 35 catalog checks — a broad technical‑SEO surface (crawl/URL inventory, broken links, redirects, indexation, metadata, canonicals, headings, hreflang, structured‑data validity), plus Deque axe‑core accessibility, a Response‑vs‑Render check, duplicate content, and Lighthouse performance. Its blocker for Snurra is integration: no REST API and no CLI (confirmed by Sitebulb’s own FAQ and long‑open feature requests). Programmatic access is limited to Cloud webhooks — an “Audit Finished” callback carrying aggregated audit‑level data, not per‑URL results — a Looker Studio connector, and a forthcoming MCP server (read/query, not a crawl trigger). Realistic wiring is out‑of‑band: schedule audits and ingest auto‑exported CSV/Excel, or receive the aggregated webhook. Pricing: Desktop Lite/Pro (14‑day trial), Cloud from £95/mo, metered by monthly URL volume + seats. It does not do consent‑timing behaviour, tag governance, SSL/DNS validity, uptime, or visual regression.

01 · What Sitebulb actually does

Capabilities

Two layers matter for embedding: what the crawler audits (the Hints and reports it produces per URL) and its automation surface (how — or whether — a backend can drive it and get data out). Toggle between them:

Crawl & URL inventory

Crawls a site with an HTML or Chrome (JavaScript) crawler on the same Evergreen Chromium engine as Google, inventorying every URL, internal‑link graph, resources and documents. Up to 500k URLs/audit Desktop (raisable), 10m Cloud.

Indexability & Hints

300+ prioritised Hints across Indexability, Links, On Page, Redirects, Internal, XML Sitemaps and more — robots.txt vs crawl, canonicals, redirect chains/loops, broken links & 404s, duplicate/missing titles & meta, heading structure.

300+ HintsSeverity

Structured data

Extracts JSON‑LD and Microdata and validates from two angles: Schema.org spec (S‑tagged) and Google rich‑results guidelines (G‑tagged). Also a standalone tool replacing Google’s retired Structured Data Testing Tool.

Schema.orgGoogle rich results

International (hreflang)

Dedicated hreflang checker: reciprocal‑pair validation, missing return tags, conflicting/ invalid annotations across every crawled locale.

Accessibility (axe‑core)

Accessibility Hints powered by Deque’s axe library — 95+ automated checks, coverage up to WCAG 2.2 AAA, selectable standard, each Hint linked to Deque University. Requires the Chrome crawler.

The Performance report captures Core Web Vitals and runs a Lighthouse audit per URL — a Performance Score split into Opportunities and Diagnostics (page weight, render‑blocking, image optimisation).

Compares the raw HTML response against the JavaScript‑rendered DOM — surfacing content that only appears after client‑side rendering. Plus a Code Coverage report for unused CSS/JS.

The defining strength (for embedding)

Sitebulb’s verdicts are deterministic crawl output: a URL returned 404, a canonical is self‑referential (or not), a title is missing/duplicated, an axe rule failed, a JSON‑LD block is invalid against Schema.org, an hreflang pair is non‑reciprocal — no human, AI‑text or visual judgment. Its accessibility (axe‑core) and structured‑data (Schema.org + Google) validators are the same engines a DIY build would use, wrapped in a mature crawler. The weakness is purely how you get the data out — covered next.

No public REST API

Sitebulb’s FAQ, on full data/API access: “Not yet, no.” There is no documented endpoint to trigger a crawl or pull per‑URL results. This is the defining integration constraint — like Screaming Frog, it is fundamentally an app, not a service.

No API

No CLI

Command‑line / headless‑trigger support exists only as open feature requests on Sitebulb’s own board (first asked 2019, still “under consideration”) — not a shipped feature. You cannot script a crawl from a pipeline.

Feature request

Cloud webhooks

Sitebulb Cloud posts an “Audit Finished” callback (plus progress/error events) carrying aggregated audit‑level data to your URL. The closest thing to a completion signal — but not per‑URL Hints, and you must build the receiver.

How Snurra would actually drive it

There is no ProviderAdapter shape here — no request to build, no JSON response to map. The only realistic wiring is out‑of‑band: (a) schedule audits (Pro/Cloud) and have Snurra ingest the auto‑exported CSV/Excel from a shared folder, or (b) stand up a receiver for Cloud’s aggregated “Audit Finished” webhook and treat it as a trigger to fetch/parse the export. Neither returns per‑URL data over HTTP on demand. Treat Sitebulb as a scheduled, file‑based data source, degrade to not‑applicable when no fresh export exists, and note the Desktop app is machine‑bound (local CPU/RAM) — Cloud removes that but still has no per‑URL API.

Standards & frameworks it relies on

Deque axe‑core → WCAG 2.0/2.1/2.2 (A→AAA, selectable). Schema.org spec + Google Rich Results guidelines for structured‑data validation (JSON‑LD, Microdata). Google Lighthouse + Core Web Vitals for the Performance report. robots.txt / XML Sitemap standards, hreflang annotations, HTTPS / mixed‑content. Google Search Console & GA4 integrations overlay real search/engagement data onto crawls (orphan‑URL discovery). 02 · Applicability — how it slots into Snurra

Embedding paths, ranked

Unlike PageSpeed / ObservePoint / BrowserStack, Sitebulb is not an HTTP service you wrap in a ProviderAdapter — there is no API to trigger a crawl or fetch per‑URL data. The ranking below is therefore about the least‑bad out‑of‑band wiring, not a live adapter.

Path
What it's good for

Scheduled audit → auto‑export → ingest files (Desktop Pro / Cloud → shared folder → Snurra parses CSV/XLSX)
The only path that yields per‑URL data. Schedule recurring audits, auto‑save exports to a shared/cloud folder on finish, and have Snurra ingest and parse the CSV/Excel out‑of‑band. Delivers the full crawl / technical‑SEO / axe‑core / structured‑data / performance surface — just on a schedule, not on demand.
Best available
Cloud “Audit Finished” webhook (aggregated payload → trigger ingest)

When released, lets an assistant query audit data in natural language. Useful for ad‑hoc analysis, not a deterministic data feed — not yet available, and read‑only (cannot trigger a crawl).

Integration shape (contrast with the sync tools)

PSI is a single GET; ObservePoint is trigger→webhook→fetch. Sitebulb is neither — the adapter would be a file/inbox watcher, not buildRequest()/mapResponse(). Config (start URL, HTML‑vs‑Chrome crawler, extraction toggles, GSC/GA OAuth) lives in the Sitebulb project; a human or scheduler kicks the crawl; Snurra reacts to a new export landing in a folder (or the Cloud webhook) and parses it. Gate on “is there a fresh export for this domain?”; degrade to not‑applicable otherwise. Because the Chrome crawler is required for accessibility and structured‑data analysis (and Lighthouse for performance), those must be enabled in the project config, and the crawl is slower and heavier than an HTML‑only crawl.

06 · Which catalog checks it can cover

Coverage — held to a 100%‑certain bar

A check is listed only if Sitebulb can produce its verdict as deterministic crawl output — a status code, a canonical/redirect/indexability fact, a metadata presence/length, an axe‑core rule result, a Schema.org/Google structured‑data validation, an hreflang reciprocity check, a Lighthouse metric, a render diff or a run‑over‑run comparison — with no human, AI‑text or visual judgment. Checks where Sitebulb captures only part of the signal (e.g. “descriptive” alt text, security‑header specifics, regional‑canonical correctness) are excluded; this is the set it can cover end‑to‑end. Several require the Chrome crawler (accessibility, structured data, performance) or a configured Content Search / a second audit to compare.

Additional checks it can cover — not in the catalog

Deterministic checks Sitebulb covers that have no matching entry in checks.ts — candidate additions to the catalog. Each is referenced.

What Sitebulb does NOT cover (for Snurra)

Excluded, because Sitebulb can’t deliver these verdicts on its own: consent‑timing behaviour (tags/cookies firing before/after a consent click — it inventories markup, it doesn’t drive a CMP) · tag/analytics governance (GA4‑post‑consent, duplicate pageviews, correct‑property — it isn’t a network/dataLayer validator) · SSL certificate validity / expiry, DNS & domain‑whois (it flags mixed content, not cert chains) · uptime monitoring · visual regression · real‑device / geo content correctness · compliance meaning (PI/ISI/GDPR wording — AI‑text judgments) · and the fuller accessibility verdicts beyond axe’s deterministic rules (true keyboard operability, alt‑text descriptiveness).

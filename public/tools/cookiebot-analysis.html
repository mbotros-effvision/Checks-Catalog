Cookiebot, assessed for embedding into Snurra

Fits into Snurra: API + setup Reads only domains you own + onboarded (CBID installed, then scanned) — can't be pointed at an arbitrary client URL.

Cookiebot (by Usercentrics) is a Consent Management Platform with two decoupled halves: an automated cloud scanner that crawls a domain to discover and categorize every cookie/tracker, and a runtime JavaScript widget (consent banner + prior-consent blocking) embedded on the site. Its deterministic, machine-readable output is the categorized cookie inventory — each cookie's name, GDPR category, provider, expiry, first/third-party status, security flags and source script. Crucially for Snurra, its read-only REST API returns only the last stored scan for domains you own and have onboarded (CBID installed + scanned) — it is not an arbitrary-URL-in scanner. This page maps what it covers, how it could slot into Snurra's worker, what it costs, and — held to a strict 100%-certain bar — precisely which catalog checks it can cover.

Bottom line up front
Cookiebot's usable surface for Snurra is its cloud cookie/tracker scanner: a monthly crawl that categorizes every cookie (Necessary / Preferences / Statistics / Marketing / Unclassified) with provider, expiry, first/third-party flag, Secure/HTTPOnly attributes and the initiating script. Its data REST API is a clean read-only GET (consent.cookiebot.com/api/v1/…, api-key + domain-group serial in the URL) — but it returns the last scan for a domain you own and have onboarded; there is no arbitrary-URL scan API, no webhooks, no scheduling API, and scans are monthly (daily is a paid add-on). Held to the 100% bar it covers 2 catalog checks directly (third-party/martech footprint, and new-trackers-since-last-scan), but it unlocks a batch of net-new cookie-attribute checks the catalog doesn't yet have. It does not deliver pre/post-consent behavioral verdicts or compliance meaning.

01 · What Cookiebot actually does

Capabilities

Two decoupled layers. The cloud scanner (a monthly crawl that discovers and categorizes cookies/trackers and produces a machine-readable inventory) is the part Snurra can consume; the runtime widget (banner + blocking) is client-side behavior on the site itself. Toggle between them:

Cloud cookie scanner

Crawls the domain from the cloud simulating ~7–8 concurrent users who click all links/menus/buttons, scroll and play embedded video — capturing dynamically-set cookies, not just initial-load ones. Scans HTML pages only; a full crawl takes up to 24h.

Real crawlDynamic cookies

Cookie categorization

Every detected item is assigned a GDPR category — Necessary, Preferences, Statistics, Marketing, plus Unclassified for items with no known purpose. Categorization is the scanner's core deterministic output.

5 categoriesDeterministic

Per-cookie detail

Name & name-pattern, provider/domain, path & value, expiry (seconds/days + human description + persistent flag), first/third-party, Secure & HTTPOnly flags, purpose, and the initiator (script URL + line that set it).

Full attributesInitiator

Multi-storage detection

Beyond HTTP cookies: HTML5 Local Storage, IndexedDB, Flash LSOs, Silverlight storage, tracking pixels and ultrasound beacons — "cookies" is used as an umbrella; the real type is listed per item.

LocalStoragePixels / beacons

Scan-over-scan changes

Runs monthly by default (daily = paid add-on). Each report lists identified trackers and what changed since the previous scan, emailed to configured recipients — a deterministic month-over-month diff.

MonthlyChange report

Login-gated scanning

Can scan behind logins / cookie-walls if credentials are supplied via the support form. If a scan finds more subpages than the plan allows, the subscription auto-upgrades to the next tier.

Auth crawlAuto-upgrade

The defining strength (for embedding)

Cookiebot's deterministic verdict is an inventory fact: this cookie exists, it is category X, provider Y, expires in Z days, is third-party, lacks the Secure flag, and was set by script S. That inventory is where it is strongest. What it does not produce from a scan is a behavioral verdict — "did tracking fire before consent" — because the crawl clicks through the site to discover everything a page can set, rather than isolating the pre-consent moment. Pre/post-consent enforcement is the job of the runtime widget on the owned site, not the scan API.

Consent banner (widget)

Runtime uc.js script (data-cbid) shows the banner and captures consent, with preset templates per regulation (GDPR / CCPA / LGPD / POPIA). Runs on the site, not against arbitrary URLs.

uc.jsPresets

Prior-consent blocking

Doesn't intercept cookies directly — it disables the element that sets the cookie until the script reads the visitor's consent level. Predefined known cookies are blocked immediately on install.

Blocking engine

Cookie declaration (cd.js)

Auto-generated table of all discovered cookies + a withdraw-consent control, embedded on a page via consent.cookiebot.com/<CBID>/cd.js. Supports a CSP nonce.

cd.jsDeclaration

Cookiebot JS object

Read-only on-page API: consent.necessary/preferences/statistics/marketing, plus events OnAccept, OnDecline, CookiebotOnConsentReady, OnTagsExecuted. Server-side: read the CookieConsent cookie.

EventsConsent state

Data REST API (read-only)

Two GET endpoints: cookies (last scan's inventory as JSON) and consent stats (opt-in/opt-out counts per day). Auth = api-key + domain-group serial in the URL path. No trigger, no OAuth.

GET onlyapi key

Google Consent Mode v2

Auto-sends ad_storage, analytics_storage, ad_user_data, ad_personalization to Google on consent — a Google Gold Tier CMP, selectable inside Google Ads / Analytics / GTM.

Consent Mode v2Gold Tier

Standards it relies on

GDPR, ePrivacy Directive, CCPA / CPRA (+ other US state laws), LGPD, POPIA; IAB Europe TCF (registered/certified CMP, CMP ID 134, framework v2.2/v2.3), Google Additional Consent, and Google Consent Mode v2 (Google Gold Tier CMP partner). ISO/IEC 27001 & 27701 and HIPAA readiness are stated at the Usercentrics/company level — vendor-stated, not confirmed on a single canonical Cookiebot certificate page. There is no proprietary taxonomy beyond the five cookie categories.

02 · Applicability — how it slots into Snurra

Embedding paths, ranked

Cookiebot fits Snurra's HTTP-adapter pattern only partially. Its data API is a clean sync GET — like PSI — but it can read back only domains you've onboarded to Cookiebot (CBID installed and scanned). It cannot take an arbitrary client URL and return JSON. The ranking below is about where that constraint still leaves useful signal.

Path
What it's good for
Fit
Read-only GET adapter for domains onboarded to Cookiebot (CBID installed + scanned → GET last scan JSON)
For any domain in your Cookiebot account, a ProviderAdapter does a single GET of the cookies endpoint and maps the categorized inventory into neutral check inputs. Clean sync shape; the only gate is that the domain is onboarded and has a completed scan.
Best available
Source net-new cookie-attribute checks from the scan JSON (classification, expiry, Secure flags, first/third-party)
The richest value: the per-cookie fields (category, ExpireDays, Secure/HTTPOnly, ThirdParty, initiator) feed a batch of cookie-hygiene checks the catalog doesn't yet have. This is where Cookiebot adds the most.
Strong (net-new)
Scrape the free Cookie Checker UI for arbitrary client domains
The only way to scan a domain you don't own is the human-facing Cookie Checker web tool — which has no documented API. Driving it programmatically would be UI scraping, likely against ToS, with no stability guarantee.
Don't
Trigger a fresh on-demand scan from the API on the hot path
The API cannot trigger a scan — it returns the last stored scan. Scans are monthly (daily add-on) and take up to 24h. Any "scan now and read results inline" flow is impossible; results are inherently async and can be up to a month stale.
Can't

Integration shape (contrast with the sync tools)

Like PSI it's an HTTP GET adapter, but with a hard precondition: the domain must be a domain group in your Cookiebot account with a completed scan. buildRequest() forms GET consent.cookiebot.com/api/v1/{apikey}/json/domaingroup/{serial}/{culture}/domain/{domain}/cookies; mapResponse() walks cookies[] and maps each item's category/expiry/flags into neutral check inputs. Gate isConfigured() on the api-key + serial and on the target domain being onboarded; degrade to not-applicable otherwise. There is no webhook — treat freshness as "last monthly scan," not live. Note the API key sits in the URL path, so keep request URLs out of logs.

06 · Which catalog checks it can cover

Coverage — held to a 100%-certain bar

A check is listed only if Cookiebot can produce its verdict as a deterministic scan-inventory fact — a tracker/cookie that exists, its category, provider, expiry, flags, or a scan-over-scan diff — no behavioral pre/post-consent capture, no content-meaning, no human judgment. Cookiebot's scan is an inventory of what a site can set, not a before/after-consent behavioral test, so the catalog's many consent-timing and privacy-wording checks are deliberately excluded. The result is a short direct-catalog list and a much richer set of net-new cookie-attribute checks below.

Additional checks it can cover — not in the catalog

Deterministic checks Cookiebot's scan inventory covers that have no matching entry in checks.ts — candidate additions to the catalog. This is where Cookiebot adds the most. Each is referenced.

What Cookiebot does NOT cover (for Snurra)

Excluded, because Cookiebot can't deliver these verdicts on its own from the scan API: pre/post-consent behavioral verdicts ("no tracking before consent," "analytics fires only after consent," "CMP loads before tracking," "consent event in dataLayer," "TCF string set after acceptance" — these need a runtime before/after-consent capture, which the inventory scan does not perform) · banner presence & UX ("banner appears on first visit," "preferences remembered," "usable on mobile," "withdraw as easy as give") · compliance meaning (CCPA-vs-GDPR wording, privacy-policy content, DPO/data-rights text — AI/human judgments) · arbitrary-domain scanning via API (owned/onboarded domains only) · and everything outside cookies (SSL/DNS, performance vitals, accessibility, SEO, uptime).

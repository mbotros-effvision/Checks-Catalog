urlscan.io, assessed for embedding into Snurra

Fits into Snurra: API-native URL-in async REST API (POST /api/v1/scan/ with an API-Key header → poll GET /api/v1/result/{uuid}/), JSON out — a two-phase ProviderAdapter exactly like ObservePoint. The free community tier is non-commercial; embedding into Snurra needs a paid/commercial agreement.

urlscan.io is a website scanner and sandbox: you submit a URL, it loads the page in an instrumented headless browser and records everything the page does — every HTTP request, every contacted domain/IP/ASN, TLS certificates, cookies, the redirect chain, a full-page screenshot, the rendered DOM, the detected technology stack — then returns an overall malicious/phishing verdict (plus a Google Safe Browsing check). It is a genuine URL-in asynchronous JSON API (submit → poll result), so it embeds behind a two-phase HTTP adapter. Its strength is deterministic, evidence-backed page forensics and reputation. This page maps its capabilities, how it slots into Snurra's worker, what it costs, the commercial-use constraint, and — held to a strict 100%-certain bar — precisely which feasibility-catalog checks it can cover.

01 · What urlscan.io actually does

Capabilities

Two layers matter for embedding: what the scanner observes and concludes (the requests, connections, certificates, artifacts and verdicts it captures from a rendered page) and its automation surface (the async submit-then-poll REST API a backend drives it through). Toggle between them:

Overall verdict

An overall malicious verdict and a numeric threat score, aggregated from urlscan's own signals, community verdicts and blocklists — a single deterministic yes/no + score per scan.

maliciousscore

Phishing / brand impersonation

Detects pages impersonating known brands (login-page / phishing kits) and identifies the targeted brand. Its proprietary detector tracks 500 popular brands; verdicts are returned only for tracked brands.

phishingbrand

Google Safe Browsing

Cross-checks the URL against Google Safe Browsing and surfaces that verdict alongside urlscan's own — a second independent reputation signal.

Safe Browsing

Requests & contacted hosts

Records every HTTP request the page makes with status codes, and inventories all contacted domains, IPs, ASNs and geolocations — the full third-party request graph.

requestsIP / ASN

TLS certificates

Captures the TLS certificate per server — issuer, subject, validity window and SANs — for the main page and every contacted host.

TLSissuer

Cookies & storage

Inventories every cookie set during the page load (name, domain, flags) — a deterministic record of client-side state established by the page and its third parties.

cookies

Redirect chain

Traces the full redirect chain from submitted URL to final landing URL — every hop, status and destination — so cloaking and redirect abuse are visible.

redirectsfinal URL

Screenshot + DOM

Produces a full-page screenshot and the rendered DOM/HTML as downloadable artifacts — visual + source evidence of exactly what was served at scan time.

screenshotDOM

Technology fingerprint

Fingerprints the technology stack (frameworks, analytics, CMS, martech) via Wappalyzer-style detection — the third-party / martech footprint of the page.

Wappalyzertech stack

The defining strength (for embedding)

urlscan's output is evidence-backed and deterministic: this request returned 404, this subresource loaded over HTTP on an HTTPS page, this cookie was set, this certificate expires on this date, this page impersonates this brand. Every verdict is grounded in a captured artifact (request log, screenshot, DOM) — no opinion, no AI-text judgment. That makes it a trustworthy source for the reputation and page-forensics slice. It does not audit SEO, accessibility, performance or consent-law compliance, and its verdict is a point-in-time snapshot of one URL.

Submit API (async)

POST https://urlscan.io/api/v1/scan/ with an API-Key header and a JSON body { "url": "…" }. Returns a uuid and the result API URL — the scan runs asynchronously.

POST /scanasync

Result API (poll)

GET /api/v1/result/{uuid}/. Poll after the scan completes (roughly ~10–30s); a 404 means it's still running. Returns the full JSON result once ready.

GET /resultpoll

Auth — API-Key header

A single API-Key request header carries your key. Any public URL can be scanned — no provisioning or verification of the target site.

API-Key

Visibility control

Each scan is public, unlisted or private. Public scans are searchable by anyone; private scans are restricted to your account. All three exist on the free tier — higher daily volume needs a paid plan.

publicprivate

Search API

GET /api/v1/search/ with a query language (page.domain:, date:, …) queries the historical scan corpus — reuse prior scans instead of re-scanning.

search

Rate limits & quotas

Documented per-minute / per-hour / per-day quotas for scans, results and search, varying by plan. Exceeding them returns HTTP 429 with X-Rate-Limit-* headers.

429quotas

How Snurra would actually drive it

A two-phase ProviderAdapter just like ObservePoint: buildRequest() issues POST /api/v1/scan/ with the API-Key header and {url, visibility:"unlisted"}; the worker stores the returned uuid and polls GET /api/v1/result/{uuid}/ until it returns 200; mapResponse() reads verdicts.overall, lists.* and stats.*. Gate isConfigured() on the API key and a commercial plan; degrade to not-applicable on error or quota exhaustion. Keep scans scheduled and off the per-request hot path, and prefer unlisted/private visibility so audited client URLs aren't published to the public search index.

Integration shape (async submit-then-poll)

Same shape as ObservePoint: start a job, then poll for the result — not a single synchronous GET. buildRequest() POSTs the URL and captures the uuid; the worker polls GET /api/v1/result/{uuid}/ until ready; mapResponse() reads the verdict + lists. Gate isConfigured() on the API key and a commercial plan; degrade to not-applicable on error or quota exhaustion. Operational constraints: the per-minute/hour/day quotas (handle 429 with backoff), the visibility choice (default to unlisted/private for client URLs), and the ~10–30s scan latency — all handled by scheduling scans off the hot path and caching by URL.

03 · Technical detail — API, quotas, visibility & licensing

What integrating actually looks like

Enough to scope an integration spike. Expand for detail:

Two calls: an async submit (POST /api/v1/scan/) that returns a uuid, then a poll (GET /api/v1/result/{uuid}/) that 404s until the scan finishes and then returns the full JSON.
# 1) submit a scan (async) — returns a uuid
curl -X POST "https://urlscan.io/api/v1/scan/" \
  -H "API-Key: $URLSCAN_KEY" -H "Content-Type: application/json" \
  -d '{ "url": "https://example.com", "visibility": "unlisted", "tags": ["snurra"] }'
# → { "message":"Submission successful", "uuid":"<id>", "result":"https://urlscan.io/result/<id>/", "api":"https://urlscan.io/api/v1/result/<id>/", "visibility":"unlisted" }

# 2) poll the result (~10–30s later; 404 = still running)
curl "https://urlscan.io/api/v1/result/<id>/" -H "API-Key: $URLSCAN_KEY"
# response shape (abridged)
{ "task": { "url":"…", "visibility":"unlisted", "time":"…" },
  "page": { "url":"…", "domain":"…", "ip":"…", "country":"…", "server":"…", "status":"200" },
  "lists": { "ips":[…], "domains":[…], "urls":[…], "servers":[…], "certificates":[…], "cookies":[…], "hashes":[…] },
  "stats": { "requests": 42, "uniqIPs": 8, "secureRequests": 40, "malicious": 0 },
  "meta": { "processors": { "wappa": {…} } },
  "verdicts": { "overall": { "malicious": false, "score": 0, "brands":[…] },
    "urlscan": {…}, "engines": {…}, "community": {…} },
  "screenshot":"https://urlscan.io/screenshots/<id>.png", "task.dom":"…/dom/<id>/" }

Rate limitsFixed-window quotas per-minute / per-hour / per-day for scan / result / search, reset at the full minute, hour and midnight UTC. Only successful (HTTP 200) requests count. 06 · Which catalog checks it can cover

Coverage — held to a 100%-certain bar

A check is listed only if urlscan can produce its verdict from its captured evidence, deterministically — a request that 404'd, an HTTP subresource on an HTTPS page, the inventory of contacted third parties, the overall malicious verdict — no human, AI-text or interaction judgment. Checks needing SEO/accessibility/performance/consent context are excluded; this is the set urlscan can cover end-to-end.

Additional checks it can cover — not in the catalog

Deterministic, evidence-backed findings urlscan produces that have no matching entry in checks.ts — candidate additions to the catalog. Each is referenced.

What urlscan does NOT cover (for Snurra)

Excluded, because urlscan can't deliver these verdicts on its own: SEO (titles, meta, structured data, canonicals) · accessibility / WCAG · performance / Core Web Vitals (it's a forensic scan, not a Lighthouse run) · consent-law / cookie-compliance judgments (it inventories cookies but doesn't rule on GDPR/TCF lawfulness) · content quality / copy · and anything needing interaction or multi-page crawl (one URL per scan). Its verdict is a point-in-time snapshot of a single URL.

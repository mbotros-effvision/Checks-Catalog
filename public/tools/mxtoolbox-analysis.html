MXToolbox, assessed for embedding into Snurra

Fits into Snurra: API-native Domain-in synchronous REST API (GET /api/v1/Lookup/{Command}/?argument=… with an Authorization: <uuid> header → JSON with Passed/Failed/Warnings/Timeouts) — the simplest ProviderAdapter shape: one call per check, no polling. The catch: the free API allows DNS lookups only (Network requests = 0), so blacklist / SMTP / HTTPS checks and any real volume need a paid plan whose API quotas are not publicly published.

MXToolbox is a DNS, email-deliverability and blacklist diagnostics service — the same engine as its web “SuperTool.” You give it a domain, host or IP and a command (mx, spf, dkim, dmarc, blacklist, dns, smtp, ptr, bimi, mta-sts, tlsrpt, …) and it returns a deterministic verdict as Passed / Failed / Warnings / Timeouts arrays. It is a genuine synchronous URL-in JSON API (one GET, full result in the body), so it embeds behind the simplest possible HTTP adapter — one call per check, no job to poll. Its strength is email/DNS infrastructure posture, a domain-level layer the catalog barely touches. This page maps its capabilities, how it slots into Snurra's worker, what it costs, the free-tier DNS-only constraint, and — held to a strict 100%-certain bar — precisely which feasibility-catalog checks it can cover.

01 · What MXToolbox actually does

Capabilities

Two layers matter for embedding: the diagnostics it runs (the email-authentication, DNS-health and blacklist verdicts it produces from a domain/host/IP) and its automation surface (the synchronous lookup REST API a backend drives it through). Toggle between them:

Email authentication

Validates SPF (spf), DKIM (dkim, needs domain:selector) and DMARC (dmarc) records — the three DNS records that decide whether mail is trusted or spoofable.

SPFDKIMDMARC

Mail server (MX / SMTP)

mx lists the domain's mail exchangers; smtp connects to a mail server and checks the banner, reverse DNS, open-relay status and connection health.

MXSMTP

Blacklist (RBL) monitoring

blacklist checks a domain/IP against 100+ email blacklists (RBLs) in one call — the definitive “are we listed and why can't we send mail?” verdict. Network request — paid API tier.

blacklistRBL

DNS records & health

dns runs a DNS-health check across authoritative nameservers; a, aaaa, soa, txt, asn resolve individual record types — deterministic resolution and configuration checks.

dnsa / aaaasoa

Reverse DNS (PTR)

ptr resolves an IP back to its hostname — the reverse-DNS/PTR record that mail servers require for deliverability. A deterministic present/absent verdict.

Modern email security

Newer email-security DNS records: bimi (brand indicators), mta-sts (SMTP MTA-STS policy) and tlsrpt (an RFC 8460 TLS-Reporting record) — each a present/valid check.

Network diagnostics

http, https, ping, tcp, trace probe reachability and latency. Network requests — the paid API tier — and mostly outside Snurra's web-audit scope.

The defining strength (for embedding)

MXToolbox's output is deterministic and structured: each lookup returns Passed / Failed / Warnings / Timeouts arrays, every item carrying an ID, Name, Info and Url — a machine-readable pass/fail with a human explanation, no AI-text judgment. That makes it a trustworthy source for the email/DNS-infrastructure slice. But that slice is orthogonal to a web-page audit: it says nothing about SEO, accessibility, performance, page content or cookies. It audits the domain, not the pages.

Rate limits & codes

Daily quotas reset at 00:00 UTC; no documented per-second or concurrency cap. Codes: 200 OK, 401 bad key, 429 quota exceeded, 500 server error.

How Snurra would actually drive it

The simplest ProviderAdapter of any tool evaluated: buildRequest() issues GET /api/v1/Lookup/{command}/?argument={domain} with the Authorization header; the response is the full result, so there is no polling phase; mapResponse() reads the Failed / Warnings arrays (empty Failed = pass). One HTTP call per check, so a domain's full email/DNS posture is several parallel adapter calls. Gate isConfigured() on the API key plus a paid plan for any network command (blacklist/smtp); degrade to not-applicable on 429 (daily quota) or 401. Watch the dkim quirk — it needs a domain:selector argument, so the DKIM selector must be known or discovered first.

Integration shape (synchronous single-GET)

The one-phase adapter Snurra already models best: one GET returns the whole result — no submit-then-poll like ObservePoint/urlscan. buildRequest() forms GET /api/v1/Lookup/{command}/?argument={domain} with the Authorization: <uuid> header; mapResponse() treats an empty Failed array as pass and reads Info for detail. Because it's one call per check, a domain's posture is a handful of parallel adapter calls, budgeted against the daily DNS/Network quota. Gate isConfigured() on the key and (for network commands) a paid plan; handle 429 as quota-exhausted; and pre-resolve the DKIM selector since dkim needs domain:selector.

03 · Technical detail — API, quotas, commands & pricing

What integrating actually looks like

Enough to scope an integration spike. Expand for detail:

One call: a synchronous lookup (GET /api/v1/Lookup/{Command}/) that returns the full result in the body. Auth is a single Authorization header carrying a plain UUID (no “Bearer”).
# a lookup — synchronous, full result in the body
curl "https://api.mxtoolbox.com/api/v1/Lookup/spf/?argument=example.com" \
  -H "Authorization: 00000000-0000-0000-0000-000000000000"
# response shape
{ "UID":"…", "Command":"spf", "CommandArgument":"example.com",
  "ReportingNameServer":"…", "TimeToComplete":"…", "IsEndpoint":false,
  "Failed": [ { "ID":0, "Name":"…", "Info":"…", "Url":"…" } ],
  "Warnings": [ { "ID":0, "Name":"…", "Info":"…", "Url":"…" } ],
  "Passed": [ { "ID":0, "Name":"…", "Info":"…", "Url":"…" } ],
  "Timeouts": [ { "ID":0, "Name":"…", "Info":"…", "Url":"…" } ] }

# dkim needs domain:selector — e.g.
curl "https://api.mxtoolbox.com/api/v1/Lookup/dkim/?argument=example.com:default" -H "Authorization: $KEY"
# tcp needs a port — ?argument=example.com&port=80
Verdict logic: an empty Failed array = the check passed; each item's Info is the human explanation and Url links MXToolbox's write-up. Note: the current schema has exactly these four arrays — there is no Errors or Information array in the live docs.
DNS requestsBill to DnsRequests — a, aaaa, asn, bimi, dkim, dmarc, dns, mta-sts, mx, ptr, soa, spf, tlsrpt, txt. Email-auth checks (spf/dkim/dmarc/mx) meter as DNS, not a separate bucket. Network requestsBill to NetworkRequests — blacklist, http, https, ping, smtp, tcp, trace. The free tier has 0 of these, so blacklist & SMTP need a paid plan. dkimRequires argument=domain:selector (both parts) — the selector must be known/discovered first. tcpRequires a &port= (or argument=host:port) — both parts required. Test endpointexample.com lookups work with no API key; any other argument without a valid key returns an Invalid ApiKey error.
MeteringTwo daily counters: DnsRequests/DnsMax and NetworkRequests/NetworkMax. Poll GET /api/v1/Usage for live remaining budget. ResetLimits reset daily at 00:00 UTC. 06 · Which catalog checks it can cover

Coverage — held to a 100%-certain bar

A check is listed only if MXToolbox can produce its verdict deterministically from its Passed/Failed arrays — no human, AI-text or page-rendering judgment. Because the catalog is a website audit and MXToolbox audits the domain's DNS/email layer, the overlap is deliberately narrow: exactly one check clears the bar. Its real value is the net-new set below.

Additional checks it can cover — not in the catalog

Deterministic, evidence-backed email/DNS-posture verdicts MXToolbox produces that have no matching entry in checks.ts — candidate additions for an “Email & DNS health” pillar. Each is referenced.

What MXToolbox does NOT cover (for Snurra)

Excluded, because MXToolbox audits the domain's DNS/email layer, not the website: SEO (titles, meta, structured data, canonicals) · accessibility / WCAG · performance / Core Web Vitals · page content / copy quality · cookies & consent-law compliance · SSL certificate page-level checks (it has http/https network commands but Snurra sources SSL from SSL Labs; not claimed here without confirmed cert-expiry fields) · and anything needing page rendering, interaction or a crawl (one command, one lookup). It is an infrastructure tool, complementary to — not a substitute for — the web-page providers.

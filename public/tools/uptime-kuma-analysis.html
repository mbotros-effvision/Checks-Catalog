Uptime Kuma, assessed for embedding into Snurra

Fits into Snurra: API + setup No official monitor-management API — you self-host it and pre-provision a persistent monitor per URL (via the community Socket.IO wrapper), then poll its status-page JSON / Prometheus /metrics; it is continuous interval monitoring, not an on-demand per-URL scan.

Uptime Kuma is a free, open-source, self-hosted uptime & availability monitor — a self-hosted alternative to UptimeRobot. It repeatedly probes a target on an interval (HTTP(s), TCP port, Ping, DNS record, HTTP keyword, HTTP JSON-query, Docker, Push, database and more) and records a binary UP/DOWN heartbeat plus response time, tracks TLS-certificate expiry, fans out to 90+ notification services, and publishes public status pages. It is an availability monitor, not a site auditor — no accessibility, SEO, content, tag/consent or visual testing. This page maps what it can deterministically verdict, how it would slot into Snurra's worker, what it costs, and — held to a strict 100%-certain bar — precisely which feasibility-catalog checks it can cover.

Bottom line up front
Uptime Kuma continuously probes a configured target and records an UP/DOWN heartbeat + response time, plus TLS-cert days-to-expiry on HTTPS monitors. Held to the 100% bar it can cover 5 catalog checks — homepage uptime, API/backend endpoint health, SSL-certificate-not-expiring (two catalog entries), and DNS resolving correctly — a narrow but genuine availability/monitoring slice. The catch for embedding: there is no official REST API to create or manage monitors (an intentional design choice) — writes go through the unofficial, version-pinned community Socket.IO wrapper, while reads come from the official Prometheus /metrics endpoint and the status-page JSON API for monitors you have pre-provisioned. It runs as a self-hosted service, so it embeds as an out-of-band, continuously-polling availability layer, not a synchronous URL-in adapter. Licensing is the easy part: MIT, 100% free — you pay only for the box you run it on.

01 · What Uptime Kuma actually does

Capabilities

Two layers matter for embedding: what the monitors verdict (the reachability / status / keyword / cert / DNS signals each probe produces) and its access surface (how a backend reads results and provisions monitors, given there is no official REST API). Toggle between them:

HTTP(s) monitor

Polls a URL on an interval and marks it UP when the status code is within the accepted range (default 200–299), DOWN otherwise — recording response time in ms. Also validates the TLS certificate during the check.

UP/DOWNResponse time

Keyword & JSON-Query

HTTP Keyword = UP if a configured keyword is present in the response body. HTTP JSON Query = UP if a JSONata expression against the JSON body matches the configured condition — API-payload assertions, not just status codes.

KeywordJSONata

TCP · Ping · Docker

TCP Port = UP if a port accepts a connection. Ping = UP on ICMP reply + latency. Docker = UP if the container is running (via the Docker socket). Host- and service-level reachability below the HTTP layer.

TCPICMP

DNS Record monitor

Resolves a chosen record type (A, AAAA, CNAME, MX, TXT, NS, SOA, SRV, CAA) and marks UP on successful resolution; with an expected record value configured it goes DOWN on mismatch — deterministic resolution + drift detection.

ResolveDrift

TLS-certificate expiry

Every HTTP(s) monitor reads the certificate and computes days-until-expiry, exposed as monitor_cert_days_remaining. A configurable threshold notification fires ahead of expiry — a proactive cert-expiry alarm.

X.509Days remaining

Push (dead-man's switch)

A passive monitor: an external job pings /api/push/<token> on each success. If the heartbeat stops arriving within the interval the monitor flips DOWN — catching silent cron / background-job failures.

PassiveCron watch

Status pages & uptime %

Publishes public status pages with per-monitor status, rolling uptime percentage and an incident timeline — stakeholder-facing SLA evidence. Uptime is computed per monitor over rolling windows (e.g. 24h).

Public pageUptime %

Notifications (90+)

Fans failures/recoveries out to 90+ services — Telegram, Discord, Slack, Email/SMTP, Gotify, Pushover and a generic webhook. Per-monitor retries and "important-event only" filtering.

WebhookMulti-channel

Broader probe types

Also Websocket, Steam / GameDig, MQTT, gRPC keyword, Kafka producer, SNMP, RADIUS, Tailscale ping and databases (SQL Server, Postgres, MySQL, MongoDB, Redis) — all resolving to the same UP/DOWN heartbeat.

InfraDB

Standards & protocols it relies on

HTTP/HTTPS status semantics · TLS / X.509 certificate parsing & expiry · DNS record types (A/AAAA/CNAME/MX/TXT/NS/SOA/SRV/CAA) · ICMP, TCP, WebSocket · JSON / JSONata · Prometheus exposition format (/metrics) · SNMP, MQTT, gRPC, SQL wire protocols. It implements no WCAG / OWASP / Schema.org / Core-Web-Vitals standard.

TLS/X.509DNSPrometheus

The deterministic core (for embedding)

Each monitor's verdict is a deterministic probe: the status code was in-range (or not), the port accepted (or not), the keyword was present (or not), the JSONata condition matched (or not), the cert had N days left, the record resolved to X. No human, AI-text or visual judgment — which is exactly what makes the covered checks 100%-certain. What is configurable is the target, interval, accepted codes, keyword/JSON condition, retries and cert-alert threshold.

No AI/humanConfigurable target

No official REST API

Uptime Kuma has no built-in REST API to create/edit/delete monitors — an intentional design choice (open feature requests #644 / #1343 / #2771 / #7151). All writes go through its internal Socket.IO API, "not officially supported for third-party integrations."

By designSocket.IO

Prometheus /metrics

Official read endpoint exposing gauges monitor_status, monitor_response_time and monitor_cert_days_remaining, labelled with name/type/url/hostname/port. Auth = Basic by default, or a Bearer API key (uk2_…) once created.

GaugesBearer key

Status-page JSON API

Read-only, public if the page is published: /api/status-page/<slug> (config, groups→monitors, incidents) and /api/status-page/heartbeat/<slug> (heartbeatList + uptimeList). The cleanest read path for pre-provisioned monitors.

HeartbeatsuptimeList

Push endpoint

GET/POST /api/push/<token>?status=up&msg=OK&ping=<ms> returns {"ok":true}. The one write-ish HTTP surface — a passive heartbeat sink for jobs, not a monitor-management API.

Heartbeat in

Community wrapper

uptime-kuma-api (Python, by lucasheld — third-party) drives add_monitor / get_monitors / edit_monitor over the reverse-engineered Socket.IO API. It is version-pinned to specific Uptime Kuma releases and "breaks with updates."

UnofficialVersion-pinned

Interval & scale

Interval default 60s, minimum 20s; retries default 0 in v2 (N retries = N+1 failures before DOWN); "Upside-Down Mode" inverts the verdict. Self-hosted, so scale is host-bound (SQLite default, MariaDB in v2). Login limiter: 20 attempts/min.

60s defaultHost-bound

How Snurra would actually drive it

Not a synchronous URL-in adapter. Snurra would pre-provision a persistent monitor per target — through the UI or the community Socket.IO wrapper (accepting version-pinning and upgrade breakage) — then read verdicts out-of-band by scraping the Prometheus /metrics endpoint (Bearer uk2_… key) or the status-page heartbeat JSON for that monitor's ID. isConfigured() gates on "a monitor exists for this target + a reachable Uptime Kuma with an API key"; degrade to not-applicable when the monitor was never set up. Because it monitors on a fixed interval, treat freshness as "last heartbeat," never trigger a scan inline on the page-audit request.

02 · Applicability — how it slots into Snurra

Embedding paths, ranked

Uptime Kuma does not fit Snurra's on-demand ProviderAdapter shape (POST a URL → get a verdict). It is a continuously-polling, self-hosted availability layer: you provision monitors once, then read their accumulated state. The ranking is about the least-painful way to wire that in.

There is no on-demand trigger and no official write API; monitoring runs on a fixed interval and provisioning is heavy. Firing "check this URL now" per page-audit request is not how the tool works.

Integration shape (contrast with the sync tools)

Unlike PSI's single GET or ObservePoint's trigger→webhook, there is no request that returns a fresh verdict. The adapter is an async reader of pre-provisioned state: config lives in Uptime Kuma (the monitor's target, interval, accepted codes, expected DNS record, cert threshold), referenced by monitor ID / status-page slug. Auth is a Bearer API key (uk2_…) for /metrics; the status page is public. Provisioning has no official API — the community Socket.IO wrapper is the only programmatic write path. Gate isConfigured() on "Uptime Kuma reachable + monitor exists for this target"; degrade to not-applicable otherwise; never block a page-audit request on it.

03 · Technical detail — access surface, limits, scale & licensing

What integrating actually looks like

Enough to scope an integration spike. Expand for detail:

There is no official REST API for monitor CRUD — a deliberate, long-standing decision (feature requests #644 / #1343 / #2771 / #7151). Writes (create/edit monitors) go only through the internal Socket.IO API, exercised in practice by the third-party uptime-kuma-api Python wrapper (version-pinned; "breaks with updates"). Reads use two official HTTP surfaces plus the push sink:
# READ — status-page heartbeat JSON (public if the page is published)
curl https://uptime.example.com/api/status-page/heartbeat/<slug>

# WRITE-ish — passive push heartbeat from a job (the only write HTTP surface)
curl "https://uptime.example.com/api/push/<token>?status=up&msg=OK&ping=142"
# → {"ok": true}
Confirmed read/write surfaces: Prometheus /metrics, /api/status-page/<slug>, /api/status-page/heartbeat/<slug>, /api/push/<token>. Monitor management = community Socket.IO wrapper only.
# prometheus.yml scrape (from the official wiki)
- job_name: "uptime"
  metrics_path: "/metrics"
  static_configs:
    - targets: ["uptime.example.com"]
  basic_auth: { username: "<user>", password: "<uk2_key>" }

Status page/api/status-page/<slug> also returns config, publicGroupList (groups→monitors), incident and maintenanceList. 404 if the slug is missing/unpublished.
IntervalDefault 60s, minimum 20s. There is no on-demand "check now via API" trigger — freshness is the last scheduled heartbeat. RetriesDefault 0 in v2 (was 1 in v1); N retries means N+1 consecutive failures before DOWN. "Upside-Down Mode" inverts the verdict (default off). ScaleNo documented hard cap on monitors or concurrency — self-hosted, so bounded by the host. SQLite is the historic default (known ceilings at high monitor counts); v2 adds MariaDB/MySQL. No public per-endpoint request quota.
DeployNode.js app; primary path is Docker / docker-compose (also bare Node via npm / pm2). Default web port 3001; data in a /app/data volume (SQLite by default). Notifications90+ services out — Telegram, Discord, Slack, Email/SMTP, Gotify, Pushover, and a generic webhook. Per-monitor assignment + retries; "notify on important events only" filtering. 05 · Pricing

What it costs

Uptime Kuma is 100% free and open source under the MIT license — there is no paid tier, no seat count and no usage metering from the project. The only cost is the infrastructure you self-host it on. The project ships no first-party managed SaaS; third-party one-click hosting exists and is flagged as such.

06 · Which catalog checks it can cover

Coverage — held to a 100%-certain bar

A check is listed only if Uptime Kuma can produce its verdict as a deterministic probe — an UP/DOWN heartbeat, an accepted-status verdict, a cert-days-remaining value, or a DNS resolution / expected-record match — with no human, AI-text or visual judgment. Checks where it captures only part of the signal are excluded: e.g. "Uptime history tracked — 7 and 30 day percentage" (only a 24h window is confirmed via the API), "Response-time SLA breach alert" (no native soft response-time threshold — only a hard timeout → DOWN) and SSL validity "no browser warnings" (it validates the cert chain but does not replicate the full browser-warning surface). This is the set it can cover end-to-end.

Additional checks it can cover — not in the catalog

Deterministic checks Uptime Kuma covers that have no matching entry in checks.ts — candidate additions to the catalog. Each is referenced.

What Uptime Kuma does NOT cover (for Snurra)

Excluded, because it can't deliver these verdicts on its own: accessibility (WCAG), SEO / content / metadata, forms & CTAs, tag / analytics / consent governance and visual regression — none of these are monitor types · full-site crawl / broken-link scanning (it probes individual configured endpoints, not a crawl) · Core Web Vitals as a performance verdict (it records a single response-time / ping, not LCP/INP/CLS) · SSL validity as "no browser security warnings" (it validates the chain, but not mixed content / HSTS / the full browser-warning surface — only expiry is a clean verdict) · domain-registration (WHOIS/RDAP) expiry (it does certificate expiry, not domain expiry) · error-rate spike detection (single-endpoint status, not aggregate failure rates) · and any on-demand per-URL scan (it monitors continuously on an interval, with no trigger API).

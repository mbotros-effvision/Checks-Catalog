Site24x7, assessed for embedding into Snurra

Fits into Snurra: API + setup Genuine Zoho-OAuth REST API, but every result comes from a monitor you create up front (referenced by monitor_id) that polls on a schedule — no one-shot URL-in scan; on-demand “Poll Now” is console/mobile-only.

Site24x7 (Zoho / ManageEngine) is a cloud full-stack monitoring & observability suite — uptime, synthetic (real-browser) page-speed & multi-step transactions, Real User Monitoring, SSL/domain/DNS health, RBL/blacklist, defacement, plus server/network/cloud/log monitoring. Checks run from 130 global locations (or an on-premise poller). It exposes a documented REST API (Zoho OAuth 2.0), but it is monitor-provisioned and schedule-driven: you create a persistent monitor and read its rolled-up status/reports — not a URL-in/verdict-out scanner. This page maps its capabilities, how it slots into Snurra’s worker, what it costs, and — held to a strict 100%-certain bar — precisely which feasibility-catalog checks it can cover.

Bottom line up front
Site24x7 monitors a site from 130 global locations and, held to a deterministic bar, can cover 14 catalog checks — its strength is the availability / SSL-domain-DNS family (1-min uptime, uptime %, response-time SLA, backend-endpoint health, SSL-cert & domain expiry, DNS-change), plus real-Chrome Core Web Vitals (LCP/CLS), mixed-content detection and content-vs-baseline defacement. It is a real SaaS with a documented REST API (base www.site24x7.com/api, Zoho-oauthtoken auth, version=2.0) with IT-Automation webhooks, scheduling and a Terraform provider — so it embeds behind an HTTP adapter, but two-phase and provisioned: create the monitor, then poll current_status / reports it collects on its schedule. Pricing is per “basic monitor” unit (a website is ≈$0.36/mo a-la-carte) with a free-forever tier. It does not do SEO crawling, tag/analytics/consent governance, visual regression, or WCAG conformance (only Lighthouse’s automated a11y score).

01 · What Site24x7 actually does

Capabilities

Two layers matter for embedding: what the monitors measure (the availability, timings, certificates, DNS records and page metrics they capture from real locations/browsers) and its automation surface (the REST API, IT Automations, webhooks and scheduling a backend drives it through). Toggle between them:

Uptime / availability

HTTP/HTTPS (and ping/port/protocol) monitors poll a URL as often as every 1 minute from up to 130 locations, verdicting up/down/trouble + availability %, with a response-time breakdown (DNS, connect, SSL handshake, first byte, download).

1-min · 130 locationsResponse breakdown

Web Page Speed (Browser)

Loads a URL in real Chrome and records the resource waterfall, page size & request counts, Core Web Vitals (FCP/LCP/CLS) + TBT, a rendered screenshot, unsecure (mixed-content) resources, and Lighthouse scores (Perf / A11y / Best-Practices / SEO / PWA).

Real ChromeCWV + Lighthouse

Web Transaction (Browser)

Record a user path or import a Selenium IDE script and replay a multi-step flow (login, add-to-cart, form submit) on real Chrome/Firefox/Edge across locations — availability & timing per step.

Multi-stepSelenium

SSL / TLS certificate

Tracks days-to-expiry, validates the trust chain, OCSP revocation, a changed SHA-1 fingerprint (tamper), blacklisted CA, and protocol/cipher strength — alerting a configurable number of days before expiry.

Expiry + OCSPCipher/chain

Domain & DNS

A domain-expiry monitor tracks the registration date; a DNS monitor resolves the domain’s records and can assert them against expected values, alerting on an unexpected change.

Blacklist (RBL) & defacement

An RBL monitor checks a host/IP against 20 DNSBLs and alerts on a listing. A defacement monitor snapshots a page’s DOM (images, scripts, anchors, iframes, links, text) as a baseline and alerts when content changes beyond a threshold.

Passive telemetry from real visitor browsers/devices — field LCP / INP / CLS, page/geography/browser breakdowns and session replay. Requires the RUM JS snippet installed on the site.

Assert a keyword / regex is present or absent in the response, match an expected HTTP status code, follow redirects (up to 10), and monitor TCP/UDP ports & internet services (SMTP/POP/IMAP/DNS/NTP/WebSocket).

Standards it relies on

Site24x7’s verdicts key off formal standards: Core Web Vitals (LCP/INP/CLS — RUM; FCP/LCP/CLS — synthetic lab), Google Lighthouse (Performance / Accessibility / Best-Practices / SEO / PWA scores), SSL/TLS validation (OCSP revocation, SHA-1 fingerprint, protocol/cipher, blacklisted-CA), 20 DNSBL/RBL blacklists, and configurable HTTP status codes. It is deliberately a monitoring suite — not a WCAG-conformance, SEO-crawl or consent-governance engine.

How Snurra would actually drive it

A ProviderAdapter that is provisioned + polled, not one-shot: on first use it POSTs a monitor (URL + threshold/notification/location profiles) and stores the returned monitor_id; thereafter mapResponse() reads GET /api/current_status/<id> (or a summary/SLA report) on Snurra’s own schedule and maps the per-monitor attributes into neutral check inputs. Gate isConfigured() on a valid Zoho OAuth token + the account’s data-center base URL; reuse the access token (refresh on expiry) and back off — the API can answer over-limit with HTTP 200 + an “access denied” body rather than 429. Never create/poll a monitor inline on the per-request hot path.

02 · Applicability — how it slots into Snurra

Integration shape (contrast with the sync tools)

Unlike PSI’s single GET, Site24x7 is provisioned + scheduled: the adapter creates a monitor (or references an existing monitor_id) and later reads GET /api/current_status/<id> or a summary/SLA report — results arrive as per-monitor attribute arrays (key off attribute_label/unit, the schema has changed over time). Auth is Zoho OAuth 2.0 against the account’s data-center-specific base URL. There is no published numeric rate limit, and over-limit can return HTTP 200 + “access denied” rather than 429 — so reuse the access token and treat any denial body as back-off. Gate isConfigured() on the token + base URL; degrade to not-applicable when a monitor isn’t provisioned or a poll hasn’t completed.

03 · Technical detail — API, rate limits, monitors & licensing

What integrating actually looks like

Enough to scope an integration spike. Expand for detail:

Base https://www.site24x7.com/api (use the account’s data-center domain: .eu / .in / .net.au / app.site24x7.jp / .ca / app.site24x7.uk / .ae / .sa / .cn). JSON only; every request sends Accept: application/json; version=2.0 and a Zoho OAuth bearer.
# 1) create a monitor — a PERSISTENT object referenced by monitor_id
curl -X POST https://www.site24x7.com/api/monitors \
  -H "Accept: application/json; version=2.0" \
  -H "Authorization: Zoho-oauthtoken <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{ "display_name":"Client site", "type":"URL",
      "website":"https://example.com", "check_frequency":"1",
      "location_profile_id":"…", "threshold_profile_id":"…",
      "notification_profile_id":"…", "user_group_ids":["…"] }'

# 2) later, read the rolled-up status the monitor has collected
curl "https://www.site24x7.com/api/current_status/<monitor_id>" \
  -H "Accept: application/json; version=2.0" \
  -H "Authorization: Zoho-oauthtoken <ACCESS_TOKEN>"
Confirmed resources: monitors (CRUD), current_status (per-monitor + by group/type, e.g. type/SSL_CERT), and summary / performance / SLA / reports/alarm. 06 · Which catalog checks it can cover

Coverage — held to a 100%-certain bar

A check is listed only if Site24x7 can produce its verdict as a deterministic measurement from one of its monitors — a reachability/response-time poll, a certificate/domain/DNS check, a real-Chrome metric (LCP/CLS/unsecure-resource), or a DOM-vs-baseline diff — no human, AI-text or visual judgment. Checks where Site24x7 captures only part of the signal (or needs a whole-site crawl / tag-governance / compliance-meaning it doesn’t do) are not listed here; this is the set it can cover end-to-end. Each verdict assumes the relevant monitor is provisioned and has polled at least once.

Additional checks it can cover — not in the catalog

Deterministic checks Site24x7 covers that have no matching entry in checks.ts — candidate additions to the catalog. Each is referenced.

What Site24x7 does NOT cover (for Snurra)

Excluded, because Site24x7 can’t deliver these verdicts on its own: whole-site SEO crawl (broken-link/redirect-chain mapping, metadata/canonical/hreflang/structured-data completeness across pages — it monitors specific pages, it isn’t a crawler) · tag / analytics / consent governance (GA4 firing, correct-property, pre-consent tracking, CMP load order — it’s not a consent scanner) · compliance meaning (CCPA-vs-GDPR wording, privacy-policy, REMS/ISI/PI — AI-text judgments) · geo content correctness (it can check from a geo, but “US visitor must not see EU content” is an AI/human verdict) · visual regression · accessibility conformance (only Lighthouse’s automated a11y score, not a WCAG engine) · and form / functional interaction beyond a Selenium transaction you author yourself.

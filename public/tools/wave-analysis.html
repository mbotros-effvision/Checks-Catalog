WAVE (WebAIM), assessed for embedding into Snurra

Fits into Snurra: API-native URL-in synchronous GET — one call returns the full accessibility report — a drop-in ProviderAdapter like PageSpeed; each scan spends 1–3 WAVE credits, so meter usage.

WAVE is WebAIM's web-accessibility evaluation engine, offered as a hosted REST API — you send it a page URL and it renders the page (after CSS/JS) and returns a structured breakdown of WCAG accessibility errors, colour-contrast failures, alerts, features, structural elements and ARIA, each mapped to a WCAG 2.1 guideline. It is a genuine URL-in, synchronous JSON API (single GET) — so it embeds cleanly behind an HTTP adapter like PageSpeed. Its strength is deterministic, single-page automated accessibility auditing from a trusted non-profit engine. This page maps its capabilities, how it slots into Snurra's worker, what it costs, and — held to a strict 100%-certain bar — precisely which feasibility-catalog checks it can cover.

Prepared: 29 Jul 2026 Use case: Automated WCAG accessibility auditing for the Snurra Site Audit Catalog: feasibility-app · 217 checks
Bottom line up front
WAVE takes a URL and returns a deterministic WCAG accessibility report — errors, contrast failures, alerts, features, structural elements and ARIA, each mapped to a WCAG 2.1 guideline. Held to a 100%-certain bar it maps to 4 catalog checks (colour contrast, image alt text, the automated-WCAG scan, heading structure), but its real value is net-new: a full taxonomy of specific WCAG failures (empty links/buttons, unlabelled form inputs, broken ARIA references, missing table headers) that the catalog's single "axe scan" check doesn't itemise. It is a true URL-in synchronous REST API (GET wave.webaim.org/api/request?key=&url=, JSON) — the cleanest possible adapter, one GET in, one report out. Pricing is credit-metered — 100 free credits, then ~$0.025–0.04/credit (1–3 credits per scan). It is a single-page static audit: no keyboard-operability, no focus-order walk, no multi-page crawl.

01 · What WAVE actually does

Capabilities

Two layers matter for embedding: what the engine evaluates (the WCAG errors, contrast failures and structure it detects in a rendered page) and its automation surface (the single URL-in REST call a backend drives it through). Toggle between them:

Errors

Definite accessibility failures that will impact users — missing alternative text, empty links/buttons, missing form labels, missing document language, empty headings. Each returned with its WCAG success criterion.

WCAG failuresDeterministic

Contrast Errors

Computes the contrast ratio of text against its background and flags any text below the WCAG AA 4.5:1 threshold. Report types 3/4 return the exact ratio and element location.

4.5:1 ratioComputed

Alerts

Probable issues needing review — skipped heading levels, redundant links, suspicious alt text, very small or justified text, missing fieldset/legend. Not definite failures, but flagged deterministically.

Review items

Features

Elements that improve accessibility when present — alt text supplied, form label associated, ARIA labels, table headers. Confirms good practice, not just failures.

Good practice

Structural Elements

Inventories page structure — every heading (H1–H6), lists, regions, iframes and other landmarks — so heading outline and document structure can be validated.

HeadingsRegions

ARIA

Reports ARIA roles and attributes present on the page and flags broken ARIA references (aria-labelledby/describedby pointing at IDs that don't exist).

ARIA roles

WCAG 2.1 mapping

Every returned item maps to a WCAG 2.1 success criterion (A/AA/AAA), retrievable in detail from the companion /api/docs endpoint. Also aligns with Section 508.

WCAG 2.1Section 508

Renders the real page

Evaluates the computed page after CSS & JavaScript (not raw HTML), at a configurable viewport width and evaluation delay — so dynamically-injected content is assessed.

Post-CSS/JS

Element locations

Higher report tiers return the exact DOM location of each issue — XPath (type 3) or CSS selector (type 4) — plus contrast values, so findings are actionable.

XPath / CSS

The defining strength (for embedding)

WAVE's verdict is a deterministic static evaluation: the image has no alt attribute (or it does), the contrast ratio is 3.9:1 (below 4.5:1), the form input has no associated label, the ARIA reference points at a missing id — no human, AI-text or visual judgment. That makes it a trustworthy source for the automatable slice of WCAG. It does not test keyboard operability, focus order or anything requiring interaction — automated tools catch only a portion of all WCAG issues.

REST API (single GET)

Base https://wave.webaim.org/api/request. One synchronous GET with url + key returns the full report as JSON (or XML). No job, no polling — the simplest possible integration.

JSONSync

Auth — API key

Register for a key; pass it as the key query parameter. HTTPS supported. No OAuth, no account provisioning of the target — any public URL works.

key param

Report types 1–4

1 = statistics (counts, AIM score); 2 = itemised issue types; 3 = adds XPath + contrast data; 4 = CSS selectors. Depth chosen per call; 1–3 credits each.

Depth control

Render controls

viewportwidth (default 1200), evaldelay (ms, default 250) and useragent override let you audit responsive layouts and JS-injected content deterministically.

viewportdelay

Authenticated pages

Optional username/password parameters let WAVE evaluate HTTP-authenticated pages — useful for staging environments behind Basic auth.

HTTP auth

Stand-alone API

The engine can be licensed to run on your own server — unlimited pages, including intranet, non-public and secure pages the hosted API can't reach.

Self-host

How Snurra would actually drive it

A ProviderAdapter exactly like the PageSpeed one: buildRequest() issues a single GET to wave.webaim.org/api/request?key=&url=&reporttype=2; mapResponse() reads the categories (error / contrast / alert / structure / aria) and maps them to neutral check inputs. Gate isConfigured() on the API key and remaining credit balance; degrade to not-applicable on error or exhausted credits. Cache per URL and keep to ≤2 simultaneous requests to avoid rate limiting — because each call spends a credit, run accessibility scans off the per-request hot path.

Integration shape (a textbook sync adapter)

This is the same shape as PageSpeed: a single synchronous GET, URL in, JSON out — no async job, no webhook, no pre-provisioned target. buildRequest() builds the query string; mapResponse() reads statistics + categories. Gate isConfigured() on the key and credit balance; degrade to not-applicable on error/exhaustion. The only operational constraints are the credit budget (1–3 per scan) and the ≤2 simultaneous request guidance — both handled by scheduling scans and caching by URL.

03 · Technical detail — API, credits, limits & licensing

What integrating actually looks like

Enough to scope an integration spike. Expand for detail:

Base https://wave.webaim.org/api/request, JSON (or XML). One synchronous GET; the report is in the response body — there is no job/poll step.
# single synchronous request — returns the full report as JSON
curl "https://wave.webaim.org/api/request?key=$WAVE_KEY\
  &url=https://example.com/page\
  &reporttype=2&format=json&viewportwidth=1200"

# response shape (abridged)
{ "status": { "success": true, "httpstatuscode": 200 },
  "statistics": { "pagetitle":"…", "pageurl":"…", "creditsremaining": 97, "allitemcount": 42, "totalelements": 812, "waveurl":"…" },
  "categories": {
    "error": { "count": 5, "items": { "alt_missing": {"count":3, "xpaths":[…]}, "label_missing": {"count":2} } },
    "contrast": { "count": 7, "items": { "contrast": {"count":7, "contrastdata":[…]} } },
    "alert": {…}, "feature": {…}, "structure": {…}, "aria": {…} } }
Request parameters: key, url (required); reporttype (1–4), format (json/xml), viewportwidth (default 1200), evaldelay (ms, default 250), useragent, and username/password for HTTP-authenticated pages.
Type 11 credit — statistics only: item counts per category, total elements, page title, AIM score, credits remaining. Type 22 credits — adds an itemised breakdown: each distinct issue type and its count within every category. Type 33 credits — adds XPath locations for each item plus contrast-ratio data. Type 43 credits — as type 3 but with CSS selectors instead of XPath for locating elements.
ExecutionSynchronous. The GET returns the finished report — no async job, no webhook, no polling. Latency is one page render (tune with evaldelay). ConcurrencyWebAIM asks callers to keep to ≤2 simultaneous requests; exceeding it may trigger rate limiting. Serialise/queue scans accordingly. MeteringBilled in credits (1–3 per scan by report type), decremented from the account balance — creditsremaining is returned on every call.
ScopeOne page per call. WAVE evaluates a single URL — there is no crawl; Snurra supplies each URL to audit. Scheduling / webhooksNone built in. Being a plain sync API, scheduling and retries live on Snurra's side (the worker decides when to scan). Stand-alone APIThe engine can be licensed for on-server use — unlimited pages incl. intranet/secure/non-public, no per-credit cost. The route to high volume and private pages. Batch (AIM)For large one-off audits WebAIM offers an AIM Report (up to 20,000 pages for a flat fee) — a managed batch, not an API surface.

06 · Which catalog checks it can cover

Coverage — held to a 100%-certain bar

A check is listed only if WAVE can produce its verdict as a deterministic static evaluation — an image with no alt attribute, a contrast ratio below 4.5:1, a heading structure, a WCAG-mapped failure — no human, AI-text or interaction judgment. Checks that need keyboard operability, focus order or content-meaning are excluded; this is the set WAVE can cover end-to-end.

Additional checks it can cover — not in the catalog

Deterministic WCAG failures WAVE detects that have no matching entry in checks.ts — candidate additions to the catalog. Each is referenced.

What WAVE does NOT cover (for Snurra)

Excluded, because WAVE can't deliver these verdicts on its own: keyboard operability & focus order (it is a static engine — no interaction, no Tab walk) · screen-reader behaviour · cognitive / content-meaning WCAG criteria (reading level, meaningful link text, alt quality — human judgment) · multi-page crawl (one URL per call) · visual regression · and everything outside accessibility (performance, SEO, security, consent). Automated tools catch only a portion of WCAG issues; full conformance still needs a manual audit.

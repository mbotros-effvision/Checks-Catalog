Percy by BrowserStack, assessed for embedding into Snurra

Fits into Snurra: API + setup Driven by the Percy SDK in your own test render (not a plain URL); result is a baseline-dependent diff a human approves — no one-shot URL→verdict.

Percy is a visual‑regression engine. It captures a DOM snapshot during your existing tests, re‑renders it across real browsers and responsive widths in its own cloud, and pixel‑diffs each render against an approved baseline. It never drives or asserts application behaviour itself — it answers one question deterministically: has the rendered appearance changed since the last approved baseline? — and a human adjudicates the flagged diffs. This page maps its capabilities, how it slots into Snurra's audit worker, what it costs (billed per screenshot), and — held to a strict 100%‑certain bar — exactly which feasibility‑catalog checks it can cover.

Prepared: 26 Jul 2026 Use case: Visual‑regression / "looks‑right" signal for the Snurra Site Audit Catalog: feasibility‑app · 217 checks
Bottom line up front
Percy is not a scanner and not a functional test runner — it needs your test/CLI to load the page, and it produces exactly one kind of verdict: a deterministic visual diff against an approved baseline. That makes its value narrow but real: it covers precisely the "looks‑right / unchanged‑since‑baseline" checks — visual regression of key pages, hero/image swaps, unexpected banners & overlays, and responsive layout at configured widths. The catch: every check becomes a regression monitor (Percy is 100% reliable at detecting a change; a human approves or rejects each flagged diff), it bills per screenshot (snapshot × browser × width — so 4 browsers × 3 widths = 12× per page), and it does zero functional, performance, SEO, accessibility, security or content‑text judgment.

01 · What Percy actually does

Capabilities

Two layers matter for embedding: the visual engine (how it captures and diffs a page) and the review & baseline workflow (how a change becomes a verdict). Toggle between them:

DOM snapshot, not a raw screenshot

Percy's SDK captures the DOM + CSS + assets during your test, ships them to Percy, and re‑renders server‑side. Because the DOM is stored, it can re‑render at any width later.

DOM snapshotServer‑side render

4 rendering browsers

Renders in Chrome, Firefox, Edge and Safari — all enabled by default for new projects. Rendering happens in Percy's cloud, so it adds no time to your CI run.

Cross‑browserSafari

Responsive widths

Re‑renders the same snapshot at as many configured widths as you want (e.g. 375 / 768 / 1440). For viewport‑dependent DOM, responsiveSnapshotCapture captures per width.

ResponsiveConfigurable widths

Snapshot stabilization

Proprietary stabilization freezes animations/GIFs and handles anti‑aliasing & dynamic data to minimise false positives — so a diff means a real change.

Freeze motionFewer false diffs

Pixel diff vs baseline

Compares each new render against the last approved baseline and highlights changed pixels in a side‑by‑side UI (baseline left, new right). Detection is deterministic.

Standards & protocols it builds on

No formal compliance standard — Percy is a rendering / diff engine. It rides the W3C WebDriver / Selenium protocol and framework SDKs (@percy/playwright, @percy/cypress, @percy/selenium-webdriver, @percy/puppeteer), serializes the DOM via @percy/dom, and re‑renders across Chrome / Firefox / Edge / Safari engines at configurable responsive widths.

W3C WebDriverSDK modelCross‑browser engines

The defining constraint

Percy does no functional driving and no autonomous judgment beyond the pixel diff. It will not click, submit, route, or tell you a CTA is broken — you load and script the page with an existing test or the @percy/cli. Percy only answers "did the rendered pixels change vs the approved baseline?" — and even that verdict is finalised by a human approving or rejecting each flagged diff.

Approved‑baseline model

The baseline is the last approved build — dynamic, not a fixed golden image. Each new build diffs against it; approving a build makes it the next baseline.

Branch‑aware baselines

Feature branches track separate baselines, so changes on main don't pollute a branch's diff. Percy uses PR/commit metadata to pick the right baseline.

Auto‑approve on main

Builds on the production branch are auto‑approved by default; "approval‑required branches" force human sign‑off. (Don't set one branch as both.)

Deterministic detect, human verdict

Unchanged snapshots pass without review; a human approves / requests changes only on flagged diffs. Approvals are per‑snapshot and generally irreversible.

Snapshot‑level approval

You approve a snapshot (which bundles all its browser × width screenshots), not an individual screenshot — and an identical snapshot is reviewed only once across a branch.

SCM status checks

GitHub / GitLab / Bitbucket PR checks stay pending until visual review; approving in Percy updates the commit/PR status — a natural CI gate.

What "100% covered" means for Percy

For a Snurra check, Percy is 100% reliable at the deterministic half — detecting whether a page's rendered appearance departed from its approved baseline. The acceptability of a flagged change is a human decision. So these checks become regression monitors that never miss a visual change, rather than fully autonomous pass/fail checks — which is exactly right for the "unchanged / looks‑right" family and is why the coverage list below is scoped to it.

02 · Applicability — how it slots into Snurra

Embedding paths, ranked

Snurra's worker already loads every page in headless Playwright and has an integration seam — a capability + swappable ProviderAdapter over a shared HTTP transport, with Google PageSpeed as the reference slice. Percy inverts the usual flow: the snapshot is captured inline during Snurra's render, then Percy diffs asynchronously and the result comes back by API/webhook. Integration shape (contrast with the PageSpeed & Automate slices)

Unlike PageSpeed (single GET) or BrowserStack Automate (start‑then‑poll), Percy's snapshot is captured inline during Snurra's existing Playwright render — isConfigured() gates on PERCY_TOKEN — then Percy renders/diffs asynchronously and the result arrives via the Percy build API or a webhook. Map unchanged → pass, changed → review‑flagged (never a hard run failure), first‑seen → baseline (not‑applicable). Honour graceful degradation — no token or a Percy outage returns null → not‑applicable. And budget screenshots deliberately: every page × browser × width consumes quota.

03 · Technical detail — SDK, the screenshot math, projects & rate limits

What integrating actually looks like

Enough to scope an integration spike. Expand for detail:

You keep your Playwright script; you add a snapshot call and run it under percy exec so the CLI wraps the run and uploads to Percy. Auth is the per‑project PERCY_TOKEN (write‑only).
# 1) snapshot inline during the existing render (Snurra already runs Playwright)
import { percySnapshot } from '@percy/playwright';
await page.goto(targetUrl);
await percySnapshot(page, 'Homepage — hero', { widths:[375,768,1440] });

# 2) run the suite under the Percy CLI (uploads DOM snapshots to Percy's cloud)
PERCY_TOKEN=xxxxx percy exec -- npx playwright test

# 3) read the build result back (unchanged → pass, changed → review, new → baseline)
GET https://percy.io/api/v1/builds/<build_id> # or receive a webhook

06 · Which catalog checks it can cover

Coverage — held to a 100%‑certain bar

A check is listed only if its verdict reduces to "has the rendered appearance changed vs an approved visual baseline" — the one thing Percy answers deterministically. Every listed check needs an approved baseline and runs as a regression monitor: Percy flags any visual change with certainty, and a human adjudicates whether the change is acceptable. Checks whose verdict also depends on a non‑visual portion — a click, an href, a journey, a business rule — are not listed here, because Percy can't fully cover them on its own. This is only what Percy can cover end‑to‑end.

Additional checks it can cover — not in the catalog

Deterministic diffs Percy produces that have no matching entry in checks.ts — candidate additions to the catalog. Percy detects each diff deterministically, but the pass/fail verdict is adjudicated by a human (auto-pass only when there is no diff). Each is referenced.

What Percy does NOT cover

Excluded entirely, because a visual‑diff engine cannot deliver these verdicts: functional interactions (clicks, routing, form submit, back/forward, menu behaviour) · performance vitals (LCP/INP/CLS, load time) · SEO facts (title, meta, canonical, sitemap, robots, hreflang) · SSL/TLS & security headers · Accessibility / WCAG (axe, tap‑target geometry) · text/content analysis (readability, duplicate, thin content, placeholder text, copyright year) · all AI‑text / compliance (REMS, ISI, CCPA/GDPR wording, geo content) · route/URL discovery (new/deleted pages, broken links, crawl) · geo‑IP routing · uptime / DNS / domain‑expiry · competitive benchmark · audit‑trail. Also structural: Percy needs a driver (an existing test/CLI to load pages) and an approved baseline — the first run only sets the baseline, and every flagged diff is a human decision.

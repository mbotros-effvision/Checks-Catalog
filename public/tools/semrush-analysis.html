Semrush, assessed for embedding into Snurra

Semrush is an SEO / marketing-intelligence SaaS. The part that overlaps a site audit is Site Audit — a cloud crawler (SemrushBot) that runs 140+ technical/on-page checks across crawlability, HTTPS, redirects, canonicals, hreflang, structured-data markup, broken links, internal linking, duplicate/thin content and (lab, sampled) Core Web Vitals. It exposes a real Site Audit API that launches an audit and returns both a summary and per-URL issue lists, plus Analytics / Position-Tracking / Backlink APIs for rankings and link data. This page maps its capabilities, how it slots into Snurra's worker, what it costs, and — held to a strict 100%‑certain bar — precisely which feasibility‑catalog checks it can cover.

Prepared: 27 Jul 2026 Use case: Technical-SEO crawl + rankings signal for the Snurra Site Audit Catalog: feasibility‑app · 217 checks
Bottom line up front
Semrush's Site Audit is a strong cloud technical-SEO crawler with a real REST API — you give it a domain (no code/agent access), POST /launch a run, poll for the snapshot, then fetch a summary (errors/warnings/notices + score) and a drill-down per-URL issue list for any issue. It can cover 30 catalog checks — the technical-SEO crawl surface (broken links, redirects, canonicals, metadata, structured-data validity, hreflang, HTTPS/mixed-content, sitemap/robots, internal links, duplicate/thin content, viewport) plus rankings/visibility & backlinks via the Analytics APIs. Two constraints shape embedding: the API is a Business-plan add-on (Pro/Guru have no API), and API calls cost API units (bought in packages, they expire), at 10 req/s · 10 concurrent. It does not do functional/interaction testing, visual regression, consent/tag-firing, real accessibility (WCAG is a separate App Center app, not the Site Audit API), or full-site field Core Web Vitals (lab-only, 10-page sample).

How Snurra would actually drive it

A ProviderAdapter like PSI, but async and stateful: pre-create a project/campaign, then buildRequest() POST /launch returns a snapshot_id; poll /snapshots or /info until the run finishes; then mapResponse() pulls /info (summary counts) plus /snapshot/{sid}/issue/{id} for each issue's per-URL list, mapping them into neutral check inputs. Gate isConfigured() on the API key and a Business plan with unit balance; back off on the 10 req/s limit and ERROR 132 (out of units). Because runs are async and unit-metered, schedule them off the hot path, never inline in a page-audit request.

02 · Applicability — how it slots into Snurra

Embedding paths, ranked

Semrush fits Snurra's adapter pattern — it's an HTTP service behind a ProviderAdapter, like PageSpeed / BrowserStack / Percy — with two twists: Site Audit runs are asynchronous (launch → poll snapshot → fetch), and every call is metered in API units behind a Business plan. The ranking is driven by where it adds the most signal.

Integration shape (contrast with the sync tools)

Unlike PSI's single GET, a Site Audit check is a multi-step async job with server-side state (a project → campaign → snapshot). The adapter references a pre-built campaign by project ID, launches it, polls, then fetches summary + per-issue URL lists. Config lives in Semrush (crawl scope, page limit, schedule, user-agent). Gate on API key + Business plan + unit balance; degrade to not-applicable on ERROR 132 / 403 / timeout; respect 10 req/s. Keep runs scheduled and off the per-request path.

03 · Technical detail — API, units, rate limits, projects & crawl budget

What integrating actually looks like

Enough to scope an integration spike. Expand for detail:

Base hosts: management https://api.semrush.com/management/v1/projects/{ID}/siteaudit and reports https://api.semrush.com/reports/v1/projects/{ID}/siteaudit. {ID} = project ID; auth = key=YOUR_API_KEY.
# 1) launch an audit run → returns a snapshot_id
POST https://api.semrush.com/management/v1/projects/<ID>/siteaudit/launch?key=$KEY

# 2) poll for status + summary (errors/warnings/notices counts, pages_crawled, score)
GET https://api.semrush.com/reports/v1/projects/<ID>/siteaudit/info?key=$KEY

# 3) fetch the per-URL affected-pages list for a given issue id (paginated/filterable)
GET https://api.semrush.com/reports/v1/projects/<ID>/siteaudit/snapshot/<sid>/issue/<issueId>?key=$KEY
# → Snurra maps target_url/source_url/page_id lists into neutral check inputs

06 · Which catalog checks it can cover

Coverage — held to a 100%‑certain bar

A check is listed only if Semrush can produce its verdict deterministically — a fact its Site Audit crawler extracts (status codes, redirects, canonicals, markup, hreflang, HTTPS, links, content) or a dataset its Analytics APIs return (rankings, backlinks) — no functional, visual, or human judgment. Checks where it captures only part of the signal, or where the verdict needs a different engine (WCAG, field CWV, functional), are not listed here; this is the set it can cover end‑to‑end.

Additional checks it can cover — not in the catalog

Deterministic checks Semrush's Site Audit covers that have no equivalent in the 217‑check catalog — candidate additions to it. Each is a real Semrush issue type, referenced below.

What Semrush does NOT cover (for Snurra)

Excluded, because Semrush can't deliver these verdicts from the Site Audit / Analytics APIs: functional / interaction (clicks, form submits, user flows) · visual regression · consent / cookie-timing & tag-firing (it's SEO/marketing, not a tag governor) · real accessibility / WCAG — Site Audit's "accessibility" wording means AI-bot crawlability; genuine WCAG is a separate App Center app, not the Site Audit API · field Core Web Vitals — Semrush's CWV is Lighthouse lab data sampled to 10 pages, showing TBT not true INP, so it can't verdict site-wide LCP/INP/CLS · geo-IP content routing · uptime, DNS-change monitoring, domain-whois expiry · compliance meaning (regulatory wording). Structural: the API is a Business-plan add-on and is unit-metered.

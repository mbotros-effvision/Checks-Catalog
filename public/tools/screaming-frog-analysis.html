Screaming Frog SEO Spider, assessed for embedding into Snurra

Fits into Snurra: No API No HTTP endpoint at any tier — run the licensed desktop/CLI binary headless and parse CSV/XLSX exports.

Screaming Frog is a desktop crawler — a deterministic HTML/technical‑SEO engine that crawls a site and extracts titles, meta, canonicals, redirects, hreflang, structured data, links, response headers and more. It is best‑in‑class at what it does — and the one thing that shapes its fit for Snurra is that it is a desktop/CLI application with no cloud or REST API. This page maps its capabilities, how it would slot into Snurra's worker, what it costs, and — held to a strict 100%‑certain bar — exactly which feasibility‑catalog checks it can cover.

Prepared: 26 Jul 2026 Use case: Deterministic technical‑SEO / crawl signal for the Snurra Site Audit Catalog: feasibility‑app · 217 checks
Bottom line up front
Screaming Frog is a deterministic desktop crawler, not a service — and that shapes embedding. There is no REST API: automating it means running the licensed binary headless via CLI/scheduler on a machine you control, then parsing the CSV / Excel / Google‑Sheets exports it writes (there is no JSON output, no endpoint to call). It can cover 48 catalog checks as deterministic HTML/crawl extractions — hreflang validation, near‑duplicate / readability / thin‑content, third‑party resource status & timing, new‑script & new/deleted‑page diffs, security headers and mixed content, plus the full SEO‑crawl and axe‑core accessibility surface. It does zero functional, visual, geo‑IP, uptime or native‑performance work (it only re‑exposes Google PSI), and it cannot judge compliance meaning.

The defining constraint (for embedding)

Screaming Frog is a desktop application with no cloud or REST API. It never runs as a service you call — you install the binary and drive it via CLI / scheduler on a machine you control, then parse the CSV / XLSX / Google‑Sheets files it writes. And it is deterministic static/rendered HTML analysis: it does not click, submit forms, judge visuals, route by country IP, or measure performance itself (it re‑exposes Google PSI). Its verdict for any check is whatever its crawl deterministically extracted.

How Snurra would actually drive it

Because there is no API, the worker (or a dedicated sidecar VM/container) runs the binary — e.g. screamingfrogseospider --headless --crawl <url> --config <cfg> --export-tabs … --output-folder … — on a schedule, then ingests the CSV/Sheets outputs into neutral check inputs. That is heavier than an HTTP adapter (a licensed binary + RAM/SSD + headless Chrome per run), so run it on a schedule off the hot path rather than inline per request.

03 · Technical detail — CLI, scale, "projects" & rate limiting

What integrating actually looks like

Enough to scope an integration spike. Expand for detail:

Automation is the installed binary run with no GUI. Headless/CLI requires a licence, and on a server the first‑run terms acceptance must be pre‑set in the config.
# run a headless crawl and export the tabs/bulk-exports Snurra needs
screamingfrogseospider \
  --crawl https://example.com \
  --headless \
  --config /cfg/checks.seospiderconfig \
  --export-tabs "Hreflang:All,Response Codes:All,Content:Near Duplicates" \
  --bulk-export "Security:Mixed Content" \
  --export-format csv \
  --output-folder /crawls --timestamped-output --overwrite

# → Snurra ingests the CSVs from /crawls/<timestamp>/ into neutral check inputs
Other flags: --crawl-list, --save-crawl/--load-crawl (.seospider), --save-report, --create-sitemap, and scheduler‑linked --project-name/--task-name/--google-drive-account.
Database mode (SSD)Default. Writes the crawl to disk — ≈2M URLs with an SSD + 4GB RAM allocated; scales with disk/RAM. Memory mode (RAM)≈10k–100k URLs at 2GB; "a couple hundred thousand" at 8GB. Faster for small crawls, RAM‑bound. Crawl limitsLimit Crawl Total default 5M (licensed) / 500 (free); Max URL length 10,000; Max links per URL 10,000; configurable crawl depth. Rule of thumb<200k URLs → 8GB RAM fine; >1M URLs → SSD database mode + 16GB+.
ProjectsNo cloud "project" object. Crawls are local .seospider files; the scheduler organises runs by project name + task name (which double as the Google‑Drive export folders). That's the closest analog. ConcurrencyOne crawl per running instance. Parallel crawls = launch multiple headless instances — bounded by CPU/RAM/disk, not by an explicit licence quota. 06 · Which catalog checks it can cover

Coverage — held to a 100%‑certain bar

A check is listed only if Screaming Frog can produce its verdict as a deterministic HTML/crawl extraction (a fact parsed from markup, response codes/headers, links, hreflang, structured data, a crawl diff, or a configured custom extraction) — no functional interaction, visual, geo‑IP, performance‑measurement or content‑meaning judgment. Checks where SF extracts only part of the signal — the full verdict needing config or another tool — are not listed here; this is the set SF can cover end‑to‑end.

Additional checks it can cover — not in the catalog

Deterministic checks Screaming Frog produces that have no matching entry in checks.ts — candidate additions to the catalog. Each is referenced.

What Screaming Frog does NOT cover

Excluded, because a crawler cannot deliver these verdicts: functional / interaction (clicks, form submits, user flows, consent‑accept) · visual regression (Percy's turf) · Core Web Vitals / performance — SF only re‑exposes Google PSI, not its own measurement · IP‑geolocation / geo‑routing (proxy‑only; BrowserStack's turf) · SSL cert validity / expiry, DNS & domain‑whois (SSL Labs / RDAP) · uptime / continuous monitoring (it's batch‑crawl, not a monitor) · consent/cookie‑timing checks (needs a consent‑accept flow) · and compliance meaning (REMS, ISI, GDPR wording — SF can pipe text to OpenAI/Gemini, but that judgment is the LLM's, not SF's deterministic output). Structural limits: no REST API (run the binary), and the free tier caps at 500 URLs.

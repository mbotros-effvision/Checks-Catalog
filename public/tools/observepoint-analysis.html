ObservePoint, assessed for embedding into Snurra

ObservePoint is a cloud website-scanning & data-governance platform — it renders every page in a real Chrome browser and audits the tags, cookies, network requests and data layer to validate that analytics/marketing tags fire correctly and privacy rules are met. It is a true SaaS with a well-documented REST API (audits, journeys, webhooks) — so it embeds cleanly behind an HTTP adapter. Its strengths are tag/analytics integrity, consent / pre‑consent tracking, and third‑party script health. This page maps its capabilities, how it slots into Snurra's worker, what it costs, and — held to a strict 100%‑certain bar — precisely which feasibility‑catalog checks it can cover.

Prepared: 26 Jul 2026 Use case: Tag / analytics / consent governance for the Snurra Site Audit Catalog: feasibility‑app · 217 checks
Bottom line up front
ObservePoint renders every page in real Chrome and audits the tags, cookies, network requests and data layer. It can cover 39 catalog checks, and its strength is the tag/analytics/consent family — GA4 firing post‑consent, duplicate pageviews, correct‑property (tid) validation, pre‑consent cookie/analytics firing, third‑party script 404s & timing, CMP load order, dataLayer consent events, martech footprint and console errors. It is a real SaaS with a documented REST API (base api.observepoint.com, api_key auth, v2/v3), webhooks on run completion, and scheduling — so it embeds like PSI/BrowserStack, just two‑phase (trigger → webhook/poll → fetch report). Pricing is usage‑based (page scans + journeys), quote‑oriented — plan carefully around the volume budget. It does not judge compliance meaning or do visual regression.

01 · What ObservePoint actually does

Capabilities

Two layers matter for embedding: what the scanner validates (the tags, cookies, requests and data layer it captures in a real browser) and its automation surface (the REST API, webhooks and scheduling a backend drives it through). Toggle between them:

Audits (site scan)

Crawls a designated site in real Chrome, capturing a per‑page Request Log — every network request with its tags, cookies initiated, origin, size, load time, status code and geo. The tag‑governance core.

Web Journeys

Scripted multi‑step flows (login, add‑to‑cart, form submit) built from actions + custom JS, validating firing tags, variables, cookies, console errors and dataLayer at each step. ClickAll+ expands to click every element.

Tag & Variable Rules

Assert a given tag fires on a page and that specific request variables match expected values (GA4 present, tid = production property, event params correct). Global or step‑scoped; bulk‑applied via labels.

The defining strength (for embedding)

ObservePoint's verdict for a tag/consent check is a deterministic capture in a real browser: the request fired (or didn't), the cookie was set (or wasn't), the dataLayer variable equalled X, the tag firing precedes consent (or follows it) — no human, AI‑text or visual judgment. That deterministic tag/consent capture is where it is strongest; its newer automated WCAG, light SEO‑metadata and Web‑Vitals features are real too.

How Snurra would actually drive it

A ProviderAdapter like the PSI one, but two‑phase: buildRequest() POSTs to trigger a pre‑built audit/journey run; a webhook (or a poll of /web-audits/{id}/runs) signals completion; then mapResponse() fetches the page‑summary / report and maps tag/consent findings into neutral check inputs. Gate isConfigured() on the api_key; degrade to not‑applicable if absent or a run fails. Because billing is usage‑based (page scans), schedule scans off the hot path and respect the account's overage budget — never trigger a full audit inline in a page‑audit request.

Integration shape (contrast with the sync tools)

Like PSI it's an HTTP adapter, but unlike PSI's single GET it is async: the adapter triggers a pre‑configured audit/journey, waits on the webhook ({itemId,itemType,runId}) or polls the runs endpoint, then fetches the page‑summary/report and maps it. Config lives in ObservePoint (the audit's start pages, rules, consent categories, geo) — the adapter references it by ID. Gate isConfigured() on the api_key; back off on 429; and because runs consume the page‑scan budget, keep them scheduled and off the per‑request path.

03 · Technical detail — API, rate limits, "projects" & licensing

What integrating actually looks like

Enough to scope an integration spike. Expand for detail:

Base https://api.observepoint.com, JSON, v2 and v3 (v3 preferred — better pagination/filtering). Auth is a user‑level API key.
# trigger a pre-built audit run, then fetch its report on webhook
curl -X POST https://api.observepoint.com/v3/web-audits/<auditId>/runs \
  -H "Authorization: api_key $OP_KEY" \
  -H "Content-Type: application/json"

# webhook payload on completion → { itemId, itemType:"audit", runId }
curl https://api.observepoint.com/v3/reports/page-summary/pages?auditId=<id>&runId=<run> \
  -H "Authorization: api_key $OP_KEY"
Confirmed resources: web-audits, audit runs, reports/page-summary/pages, journeys (incl. LiveConnect Journeys), plus a separate Grid Reporting API. The docs state the API exposes "all ObservePoint functionality and data"; the full endpoint catalog (rules, cookies, domains, alerts) is implied but was verified only for audits / runs / reports / journeys.
Rate limit≈100–600 requests/min per endpoint (up to 1,000 on some), enforced per API key. Over‑limit → HTTP 429; guidance is wait‑and‑retry (seconds, up to ~5 min). ExecutionAsynchronous. Triggering a run returns quickly; the actual scan completes later and signals via webhook (retries 4×) or the runs endpoint. Design the adapter as trigger‑then‑await. ScreenshotsJourneys capture per‑step screenshots (default 8s settle wait, extendable). Full‑page capture on standard audits is not clearly documented.
OrganisationNo "project" object. Work is organised into Folders → Sub‑folders (journeys must live in a sub‑folder) plus Labels for cross‑cutting grouping. That's the closest analog. Scale unitLicensing is by volume, not a fixed audit count — primarily pages scanned (annual) and Journeys executed, tracked in a Usage Report with pacing and threshold alerts. OveragesAn admin "Allow Overages" toggle blocks any run — one‑time, scheduled, or API‑initiated — that would exceed the budget. The adapter must expect runs to be refused when near the cap. ConcurrencyNo per‑key concurrency figure is published; the practical limiter is the page‑scan budget + the API rate limit, not an instance count.
RenderingEvery page renders in real Chrome (not HTTP fetch) — ObservePoint can be detected as bot traffic, so allow‑listing may be needed on protected sites. Real devicesReal Device Testing (LiveConnect) runs on actual connected devices — explicitly "not emulation" — for cross‑browser / cross‑app validation. GeolocationServer‑side location simulation (London, Dublin, Frankfurt, Northern California, and others) — used heavily for consent / geo‑privacy audits. Audit config also records viewport sizes & user agents.
WebhooksFire on audit/journey run completion (success or fail): {itemId, itemType, runId}. Configure via API (webHookUrl) or the Data Sources screen. SchedulingInitial schedule + frequency (preset or custom) on both audits and journeys. Slack / JiraAlerts to Slack channels; auto‑file Jira issues — via email‑to‑channel/issue and webhooks (Slack email needs a paid Slack plan). TealiumFormal partner integration — auto‑trigger scans when tags change in Tealium. BILoad results into PowerBI / Tableau / Looker / Domo via the API / Grid Reporting API. No native data‑warehouse (e.g. Snowflake) connector was found.

06 · Which catalog checks it can cover

Coverage — held to a 100%‑certain bar

A check is listed only if ObservePoint can produce its verdict as a deterministic capture in its real‑browser scan — a tag request that did/didn't fire, a cookie set/not‑set relative to consent, a dataLayer variable's value, a request status/timing, a resource inventory, or a scripted journey outcome — no content‑meaning, visual, or human judgment. Checks where ObservePoint captures only part of the signal — the exact verdict needing a configured Rule or Journey it can't guarantee — are not listed here; this is the set it can cover end‑to‑end.

Additional checks it can cover — not in the catalog

Deterministic checks ObservePoint covers that have no matching entry in checks.ts — candidate additions to the catalog. Each is referenced.

What ObservePoint does NOT cover (for Snurra)

Excluded, because ObservePoint can't deliver these verdicts on its own: compliance meaning (CCPA‑vs‑GDPR wording, REMS / ISI / PI, privacy‑policy content — these are AI‑text judgments, not deterministic captures) · geo content correctness (it can set the geo, but "US visitor must not see EU content" is an AI/human verdict) · visual regression · SSL cert validity / expiry, DNS & domain‑whois · uptime monitoring (it schedules scans, it isn't a 1‑min monitor) · and Core‑Web‑Vitals as a performance verdict (it captures LCP/CLS/TTFB in a single render but is a monitor, not a profiling/optimisation tool).
